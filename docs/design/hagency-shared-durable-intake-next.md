## Concrete current gaps

`management_shared_work.rs::route_shared_event_page` selects only qualified runtimes with live activity, rejects events received before that process was issued, and immediately pins each event to a runtime. `management_shared_work_schema.sql::fence_shared_work` cancels unstarted work when the one-turn process ends. Therefore merely renewing the activity lease or removing the receive-time comparison cannot retain messages while offline or carry extra messages to another process.

`workers.rs::route_with_shared` already retains verified Appservice transactions durably until routing succeeds. Returning success with no runtime marks that transaction routed. The new inbox must commit before that success. Existing assignment/event pins prevent a delivered event from being rebound; keep that invariant.

`management_shared_attempts.rs::start_shared_attempt` creates one immutable successor from a durable native start intent, exact observed stopped predecessor and aggregate budget proof. Neither a stopped receipt nor its absence identifies an explicit human Stop. The current protocol has no assignment running/paused command. Never infer auto-start permission from a stopped process.

Native review confirmed `SharedWorkItem.createdAtMs` can preserve the original receive time before the new process issue time. Native model/ledger custody does not require rewriting that timestamp.

## Closed protocol and state

Add default-off `shared_durable_intake` policy. Missing control row means legacy/manual behavior, not running. Do not seed running state on migration or infer it from old Start history.

`POST shared-execution/assignments/{id}/control` accepts `{commandId,expectedRevision,mode:"running"|"paused"}`. The manager or CURRENT assigned project administrator may arm running, after current assignment/grant/setup/admin checks. The executor owner may only Stop their exact original device; that role grants no per-agent Start or approval authority. New assignments created from an exact accepted native reserve receipt initialize running when this policy is enabled, using existing assigned-admin approval and general owner execution consent. Existing assignments migrate manual and require an explicit manager/admin Start. The manager, current assigned project administrator, or original executor owner may reduce authority by pausing. Other server-admin/coordinator/owner roles confer no implicit authority. Pausing/recovery remains available when issuance is disabled. Native local Stop must immediately restrict the retained manager too; remote Stop fences new central delivery and preserves the existing bounded in-flight cleanup contract.

The command has exact actor/device/idempotency custody and CAS. Response is `{commandId,appliedRevision,control:{assignmentId,revision,mode,runningSinceMs,updatedAtMs,origin},observedAtMs}`. Exact replay returns the original applied revision and latest control projection. GET is descriptive. Each change to running defines a new revision and receive-time floor; an event tied to that same millisecond is retained as before_running_intent because its order relative to rearming cannot be proven; repeated Start while already running never resets that floor. Stop increments revision, permanently fences current processes, invalidates prior demands, and terminally cancels unbound pending events. A fresh successor pins the exact Run revision across Matrix observation; Stop followed by Run cannot admit an older in-flight start. Event observation similarly records run_control_changed when that revision changes, retaining the original event as cancelled even if the current mode is running again. New events while paused are recorded as paused, never auto-start triggers; an explicit later Start admits only events received in its new running revision. No process receipt, usage completeness or refund is invented.

Add an immutable inbox keyed by `(assignmentId,eventId)`: generated intake ID, original room/requester/thread/body/body digest, canonical event digest, original receive timestamp, admitted control revision, and recorded disposition. Permitted lifecycle is `pending -> bound` or `pending -> cancelled/expired/blocked`; original event fields are immutable. A bound row stores one immutable runtime/work link. Existing delivered event pins are checked before insertion. A conflicting duplicate is rejected, identical replay is a no-op. No previous work is moved or replayed.

The inbox accepts only canonical verified-AS text messages under the existing manager-plus-exact-puppet-mention rule. It rechecks exact assignment/request/setup/Matrix scope after gateway observation; encrypted messages, edits, foreign senders/rooms and changed membership remain excluded. No native heartbeat is required to retain an event. Transient executor session expiry is not evidence that a message was never received: storing a pending message grants no execution authority. Revoked/replaced devices and terminal business authority must not be revived. Full current live authority remains mandatory at promotion/start/model/reply.

Queue bounds are a 24-hour pending TTL from original AS receive time, 100 pending messages and 10,000 retained audit rows per assignment; overload/storage/observation failure leaves the original AS routing job pending. Candidate pages advance past full or temporarily unavailable assignments in the same routing pass, so one full first page cannot starve later targets. Explicit terminal reasons are retained. Multi-target routing uses bounded pages excluding already recorded targets, retries while candidates remain, and checks duplicate canonical digests; more than32 matching mentions cannot be silently truncated. Expiry is persisted before admission capacity checks. A full target does not roll back or duplicate other accepted targets in the same AS batch. Queue order is original receive time plus intake ID. The 10,000-row hard cap deliberately retains the AS retry; a durable archival/retention protocol is a production activation prerequisite and deferred from A. No audit rows are silently deleted.

## Paired demand and one-turn promotion

A current exact executor polls a bounded fair assignment-scoped demand index. Each offer contains only `{version:1,demandId,assignmentId,eventId,eventDigest,controlRevision,receivedAtMs,predecessorCommandId,predecessorCommandDigest}`; it is descriptive, not a spawn lease. One pending event/head/control revision has one immutable demand. No prompt or fresh allocation is manufactured.

Native stores `demandId + digest + controlRevision -> startIntentId` before POST, and recovers that mapping on retry/restart. Demand-generated intent records are excluded from generic explicit-start polling/recovery; only the exact demand wrapper may submit them. Central retains the demand link and wrapper digest with the attempt, and promotion independently requires that binding and current Run revision. It recomputes current stopped-head and all-attempt budget under the same owner ledger; positive remaining is required, unknown old work/usage remains held. New route `shared-execution/demands/{id}/start` wraps the unchanged `SharedAttemptStartInput` with exact `demandDigest` and `expectedControlRevision`. Central checks current original device, active running revision, oldest eligible event and predecessor before and after Matrix I/O, then commits demand binding plus the existing v2 attempt in ONE transaction. The unchanged v2 command is linked to demand in a separate immutable table, not by editing original bytes.

An already-qualified unused process can receive the oldest pending event without a new process. Otherwise the exact demanded successor must qualify first. `poll_shared_work` promotes exactly one inbox row for that one-turn runtime, atomically creating its original `SharedWorkItem` and event pin. Extra events stay assignment-scoped. Result upload and Matrix reply reuse existing durable work receipts, deterministic Matrix transaction IDs and recovery. Unknown start/result/send outcomes remain retained and nonreplayable; no claim of guaranteed completion under lost evidence.

Paused or revoked control blocks legacy fresh starts as well as demanded starts; otherwise old routes would bypass Stop. Historical recover/upload stays available. A pause racing a start commits either before issuance (no new command) or after issuance (cleanup required); it never claims the already-issued effect could not occur. Native stop-before-claim must retain the existing exact attempt tombstone. Failure to prove a predecessor stopped or definitely unissued remains a visible blocker; do not synthesize a stopped receipt.

## Observed budget limit and demand blockers

The actual original assignment completed its first accepted Matrix turn with 4,813 known consumed tokens against a 4,096-token agent allocation. Complete usage is retained as 4,813; remaining is zero and the overrun is 717. This is conservative admission and liability accounting, not a hard provider token cutoff. Continuous demand must retain a budget_blocked disposition with the original event and demand/start identity, never retry with new IDs, create a new allocation, automatically top up, or claim 717 tokens were refunded. A separately approved delta top-up protocol remains absent.

The first B offer permanently binds its original predecessor ID/digest and Run revision. A concurrent unrelated Start advancing that head records head_changed on the old demand; it never silently rewrites the offer or creates a replacement native intent for the same event. The event remains retained and blocks ordered promotion until an explicit future resolution; no automatic rebase protocol is implied. When the offered exact head is already qualified, idle and unused, direct promotion to that same process does not create a successor or a start intent. Both routes require current Run revision at their actual transaction boundary.
