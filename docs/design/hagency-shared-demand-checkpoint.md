# Durable demand checkpoint B (schema17)

This isolated server checkpoint builds on frozen schema16 A. It adds paired native demand polling, an immutable original wrapper for one existing v2 start, and exact one-work promotion. It is default-disabled (`enable_shared_demands=false`) and is not activated or a claim of continuous-chat acceptance. Original reserve, v1/v2 process, work, usage and Matrix-reply contracts remain unchanged. Each successor currently starts a fresh provider thread and receives only the current work body: this is ordered automatic individual-turn execution, not contextual conversation memory. A separately versioned, bounded, same-agent/room/Matrix-thread context contract remains required.

`GET /hagency/api/v1/discovery` advertises `shared-durable-demand-v1` independently of issuance configuration. This describes protocol availability; fresh poll/start requires the existing execution/successor policies plus durable-intake and demand flags. Historical demand/work binding and explicit Stop remain available through authenticated original-device/role checks. Disabling B prevents linked fresh activity, work and Matrix reply sends; it does not erase evidence. Events already retained by intake cannot fall back to the legacy direct-delivery path when intake is disabled.

## Closed routes

All following paths have prefix `/hagency/api/v1/management/shared-execution`. The authenticated response also carries `observedAtMs`.

| Method/path | Exact input | Output |
| --- | --- | --- |
| GET `assignments/{id}/control/readiness` | no query/body | `{readiness:{control,canRun,canStop,requiresLocalStop,runBlockingReason,intakeEnabled,automaticDeliveryEnabled}}` |
| POST `demands/poll` | `{after?: assignmentId,retries?,reoffers?}` | `{demand: status|null,nextAfter: assignmentId|null}` |
| POST `demands/{id}/recover` | `{demandDigest,retries?,reoffers?}` | `{demand:status}` |
| POST `demands/{id}/start` | `{demandDigest,expectedControlRevision,start:SharedAttemptStartInput,retry?,reoffers?}` | `{delivery:SharedAttemptDelivery}` |
| POST `demands/{id}/retry` | `{demandDigest,expectedControlRevision,retry,attemptId,result:SharedAttemptResultInput}` | `{acknowledgement,demand:status}` |
| POST `demands/{id}/block` | `{demandDigest,expectedControlRevision,reason,budget,retries?,reoffers?}` | `{demand:status}` |
| POST `work/{id}/demand` | `{workDigest,runtimeCommandDigest}` | `{demand:null|{offer,demandDigest,binding}}` |

`status` contains the exact offer/digest, state, nullable runtimeCommandId, nullable binding and, once retried, `retry`. States are offered, start_committed, retry_offered, bound, cancelled, expired, head_changed, budget_blocked, usage_unrepresentable and blocked. They describe recorded progress, never fresh native authority. The block request supports budget_blocked with a valid zero-remaining aggregate or usage_unrepresentable with null budget. A current original executor can impose a restriction; this cannot add capacity or manufacture process evidence.

## Custody and ordering

One immutable AS event/assignment becomes one intake and at most one demand. The first offer binds the original Run revision and exact predecessor forever. FIFO is receivedAtMs then demandId (equivalent to the original intake ID ordering). Poll examines at most16 current original-device assignments per call, returns a rotating assignment cursor even when selected entries cannot issue, and never creates a replacement intent. A blocked event keeps its own status and notice, and later events in that Run revision continue without it. Expired pending events are retained and do not loop or block the next eligible event.

The native device privately commits the exact demand-to-start mapping before POST. Demand-generated start intents must be excluded from generic manual-start recovery. The server cannot identify an unpublished native intent; after B commit the immutable wrapper, existing v2 attempt and runtime are one atomic transaction. An exact retry returns historical delivery only. Unknown replies, replacement body/ID, stale predecessor and Stop/Run ABA never create another attempt. Current exact owner/device/generation, business assignment, original grant, setup/admin and actual Matrix membership are checked before and after network observation.

An already qualified idle head can receive one queued event directly. Otherwise the demanded successor must qualify first. The existing work poll atomically commits the original event body/thread/receive time, unchanged work bytes, original event pin and separate demand binding. A one-turn runtime receives at most one work item; the next event remains assignment-scoped for a later stopped-head demand. Native validates the descriptive binding before inbox/ACK and recomputes its full canonical ledger hold before issuing the call. Central work/activity/reply checks retain the exact Run revision, including when B is subsequently disabled. The work poll of an Agent whose authority failed is refused, with or without an applied budget, and the Agent's messages end by their own time.

A manager or current assigned project administrator may Run or Stop. The exact original execution-device owner may Stop, not Run; resource-owner consent is general and no second per-agent or per-turn human approval is introduced. Existing migrated stopped assignments remain manual until intent is established. The control command response retains the original commandId/appliedRevision with a separate latest control projection: replay never reapplies Stop after a later Run. Native Stop uses a separate private outbound journal and a monotonic local restriction through the selected revision.

## Limits retained

The live accepted example remains 4,813 consumed/retained against4,096 allocated: remaining0 and overrun717. B retains budget_blocked and creates no successor, new allocation, top-up, refund or replacement agent. This is conservative admission, not a hard provider token cutoff. Unknown bounded usage remains held; unrepresentable usage blocks without a fabricated numeric budget.

A changed immutable offer head or unresolved native custody can require explicit resolution. Uncertain process issuance, start or stop is time-bounded (below). No automatic rebase or invented stopped receipt exists. Stop cancels pending events with recorded reason; old work and reply outcomes remain auditable/nonreplayable. Schema16 queue limits remain100 pending,24h expiry,10,000 retained rows per assignment. A reviewed archive/retention policy is still required before production; this checkpoint never discards audit to make room. Native paired transport/worker and actual multi-turn acceptance are separate qualification steps.

A plain successor that `attempts/start` gives an Agent with an applied budget (that route checks no budget) gets no work, so it cannot spend outside that budget: the v2 work poll binds nothing for such an Agent and the budget work poll serves only v3 processes; until it stops, though, it is the Agent's head, and the budget queue offers nothing for the Agent.

## Mini-app control display

The readiness read is scoped to the same manager/current assigned administrator/exact execution-device owner as control. No implicit server-admin or coordinator visibility is added. `canRun` reflects known current business authority, role, intake policy and a mode change; reasons are role_required, intake_disabled, assignment_authority_changed, already_running, or null. `canStop` remains available to the authorized roles when issuance is disabled. `automaticDeliveryEnabled` describes all required server policies, not device reachability, process state, provider health, remaining budget or context memory. The UI must display the central Run/paused/manual mode separately from the latest process observation and separately observed usage/device freshness. Actual Run always rechecks real Matrix membership. The original GET control and POST control shapes are unchanged.

Authenticated management session features include `shared-run-control-v1` independently of issuance policy. This advertises the scoped control/readiness/recovery/Stop protocol; it is not authority to Run. Older servers lack that feature. General discovery independently advertises the versioned native transport capability `shared-durable-demand-v1`.

`requiresLocalStop` identifies the exact original executor owner/device cleanup identity independently of role priority or issuance policy, including a later authorized generation. It remains true when that same actor is also manager/assigned administrator. Native must durably apply its owner Stop journal/fence first and must not fall back to a generic central POST if its local selection is missing. For an unrelated manager/administrator it is false; `canRun=false` alone must never infer owner identity.

## Uncertainty time bound (2026-11-06)

Owner policy: uncertain shared execution never blocks an Agent's queue indefinitely. This covers an attempt issued but never claimed, a claim whose process state is unknown, and an unconfirmed start or stop.

- Bound: 3 minutes (`UNCERTAIN_GRACE_MS`) after the later of `expires_at_ms` (which also bounds every execute ticket), the first activity lease (at most 30 s after the window) and later process evidence the server holds (activity renewals, work acknowledge/start/complete). Observe and cleanup tickets never extend it.
- Within the bound nothing changes: the attempt stays fenced and no second process can start for its work.
- After it, the server stops a v2/v3 attempt still `pending`, `issued`, `qualified` or `unknown` by itself, on every executor poll and in the background cleanup worker. It fences the attempt and sets `stopped`. It ends a v3 demand that the attempt started (a `head_changed` terminal), and a v2 demand whose attempt reported a process (`head_changed`) unless that demand's start said that its executor takes messages back (`reoffers`, last section). A v2 demand whose attempt never reported a process waits for the executor's evidence that the attempt stopped (next section), and so does one whose start said `reoffers`, for a bounded time (last section). It writes no receipt and no usage.
- The executor then supplies explicit evidence on a cleanup ticket: `not_started` when nothing was claimed, or `stopped` with `reason: "uncertain_timeout"` and the claim's own process digest. Before the bound the server refuses the latter with `shared_attempt_timeout_pending`. A stopped attempt without such evidence stays discoverable with a cleanup ticket.
- The next attempt names that receipt as its predecessor stop (an empty `processDigest` after `not_started`). An interrupted event whose turn began is not replayed; a rare duplicate or missing reply is accepted.
- v2 now accepts `not_started` for an attempt issued but never claimed, with the same fence proof as v3, and only on a cleanup ticket after `expires_at_ms`. The `validate_shared_runtime()` trigger, re-created at every start, accepts that v2 receipt and a v2 or v3 successor that names it. There is no schema version change.

## Retry of a never-started event (2026-11-06)

ADR-193 amendment, v2 demands only: an event whose attempt provably never started runs again in place, at most 3 times (`MAX_DEMAND_RETRIES`).

- Only the executor's explicit request re-opens an event: `POST demands/{id}/retry` carries the `not_started` evidence for the demand's latest attempt on that attempt's cleanup ticket. In one transaction the server records the receipt exactly as the attempt result route does and, if the event is still current, adds `management_shared_demand_retries` row `n`. The time bound never retries anything.
- The demand keeps its id, offer, event and FIFO place. Its status becomes `retry_offered` with `retry: n`. Retry `n`'s start (`demands/{id}/start` with `retry: n`) names the never-started attempt (empty `processDigest`) and is kept in `management_shared_demand_retry_starts`. A replay returns the same attempt.
- Bindings, `current()`, `allowed()` and the sweep treat a retry start like the original start. The binding validator is replaced to accept the latest retry start.
- A fourth request ends the event: `head_changed`, block payload `"retry_exhausted"`. A claim, a qualified process or any work evidence makes an attempt ineligible for `not_started`; such an attempt is retried only under the next section.
- A `not_started` receipt on the plain result route (older executors) ends the event as before. A never-qualified attempt stopped by the time bound keeps its demand open for the executor's evidence (for a bounded time when its start said `reoffers`; see the last section).
- Discovery advertises `shared-demand-retry-v1` only while the retry route is enabled: both use `ManagementPolicy::shared_demand_retries()`.
- Wire additions are optional (`retry` on the start input and the status). A status carries `retry` or `retry_offered` only for a request that declares `retries: true` (demand poll, recover, block). For any other executor, an unbound retry ends the event (`head_changed`, block payload `"retry_unsupported"`), and a bound one reads as `bound`.
- `validate_shared_demand()` is owned by the retry schema file. Startup refuses to replace a body that a later versioned migration changed. Retry rows are inserted with explicit column lists.
- Rollback: let retries finish first. The previous binary ends an unbound retry as `head_changed` and reports a retry-bound demand with the original start's runtime. Never drop the retry tables.
- Schema: two additive tables, their triggers and the replaced validator, applied by `management_shared_demand_retry_schema.sql` at every start. There is no version change; the previous binary ignores them.
- Matrix 429 responses map to `matrix_rate_limited` (retryable, 503); the delay and endpoint name are logged, never ids or bodies.

## Retry of an event whose process ended before its turn (2026-11-26)

Time-limit rule 3 (`hagency-time-limits.md`): the line between what is redone and what is never guessed is the start of the turn, not the hand-over of the event. v2 demands only, only for an executor that says it takes messages back, and only while the operator has it switched on.

- Switch: `[management] enable_shared_demand_reoffers`, off by default. `ManagementPolicy::shared_demand_reoffers()` is the switch and every gate of `shared_demand_retries()`, and it decides each part below: discovery lists `shared-demand-retry-v2`; the retry route takes a `stopped` receipt; the demand poll holds the next message back; and the database releases. The service sets the session setting `hagency.shared_demand_reoffers` (`on` or `off`) in every transaction it runs (`Database::transaction`), and the release trigger returns at once unless it is `on`, so a binary that does not set it releases nothing. Off, demand retries (`shared-demand-retry-v1`) work as before.
- Opt-in: `reoffers: true` on the demand start input, original and retry starts alike (it is kept in the start row's payload and omitted when false, so any other start keeps its bytes), and on the demand poll, recover and block inputs. An executor sends it only while discovery lists `shared-demand-retry-v2`: a server without this change refuses the unknown field. Nothing below applies to a start without it; its message stays bound to its process and ends as before.
- Readers first (time-limit rule 6): the release before this one reads `reoffers` and acts on nothing in it. Both keep the field in the start's stored payload and in its `allocation_digest` and omit it when false, so a start without it keeps its bytes and digest (`shared_demand_reoffers_is_read_and_kept_as_sent`); a replay with the same bytes is the same start, and one that differs only in `reoffers` is `shared_demand_start_changed` (`shared_demand_start_that_says_reoffers_replays_as_sent`). A start recorded by either release is answered by the other exactly as it was, so this release goes back to that one or a later one. Every other unknown field is still refused.
- The proof is the server's record and one premise. `start` is recorded only for a process with a live activity lease, a fence ends that lease, every write holds one lock, and released work can never be started (`fence_shared_unissued_work`). The release takes that lock itself (`pg_advisory_xact_lock(5210750088328904)`, re-entrant for the service's writers), so a fence made in any other transaction waits for them. The premise is the executor's: it begins a turn only when the answer to its start request says that the start was recorded now. So work of a fenced process with no `started_at_ms` never began and never will.
- At the fence, in the same transaction, the database releases such work when three things hold: the start that began the process said `reoffers` (`shared_start_reoffers()`); the Agent serves by the rule the chat status reads for "Send again" (`shared_agent_serves(assignment, room, at_ms)`, the one definition: its assignment is `pending_native`, its control is `running`, its intent is not fenced, its ledger was not replaced, it is a `matrix_verified` member of the message's room in `shared_room_memberships`, and its reservation's time is not over at `at_ms`, read as the service's `retainable` reads it: the reserve command's end; for a pool Agent that follows its pool's grants and was reserved, the end of its run of grants, and in any case a grant of its pool in force that continues the command's; for a project Agent also the end of its allocation and of that allocation's grant. The release passes the service's clock, which only its tests set (`hagency.test_clock_ms`); the chat status passes its own time and also makes the service's whole check) and no budget result was applied to it (`shared_agent_budget_applied()`); and the work was still to run (`queued` or `acknowledged`). Trigger `fence_shared_release` on `management_shared_runtimes` copies the binding to `management_shared_demand_released_bindings`, removes the binding and the event's pin, and sets the intake from `bound` back to `pending`; the insert's own trigger checks the same conditions again. The trigger is named to run before `fence_shared_work`, which then cancels the work row. Work that a decision had already cancelled (a period turned, a budget changed) is not released, and neither is the work of an Agent whose request was withdrawn, whose ledger was replaced or that was stopped: each is recorded before the Agent's processes are fenced (a Stop changes the Agent's control first), so the message its process held ends as before (`never_started`). A release that cannot be made is skipped with a `WARNING` naming the demand and the SQLSTATE and is counted in the fence's record (below), and the event ends as before; nothing in the release can stop the fence.
- The event is a waiting event again: it keeps its FIFO place and its retry count, a Stop cancels it with the others (`explicit_stop`), and its expiry and the turn of its period end it as they end any waiting event (`event_expired`). If a budget is applied to the Agent first, it is no longer offered and no retry is opened for it (a retry opens only where its start would be accepted, which `start_refusal()` decides for both). It then ends as every message the earlier protocol had started when the budget was applied: its status reads `head_changed` from then on, the budget's queue records that end and offers the next message instead of waiting behind it, and its executor reads the end at the bound below, with the same reason (block payload `"head_changed"`).
- Nothing is offered unasked. `POST demands/{id}/retry` also takes a `stopped` receipt of the demand's latest attempt (its ordinary stop receipt, or `stopped` with `reason: "uncertain_timeout"` on a cleanup ticket after the time bound) when that attempt's start said `reoffers`; for any other start the route refuses it (`invalid_shared_demand_retry`) and records nothing, as before. `validate_shared_demand_retry()` accepts it when that attempt is stopped and fenced, its start said `reoffers`, and none of its work for this event has a start or a receipt. The retry's start names the stopped attempt with its process digest.
- An executor that uploads the stop receipt on the plain result route ends the event at its next demand poll (`head_changed`) unless it asks for the retry with that receipt before that poll (the route takes the receipt as a replay).
- A stop for work that did begin is answered on the retry route too: the receipt is recorded as on the result route (the answer says `stopped`), nothing is released, no retry is opened, and the demand stays `bound`. A replay gets the same answer.
- The next message waits for the first. While the last process holds a bound message whose turn has not begun, from a start that said `reoffers`, and that message would be given back if the process ended now (its Agent serves in its room and has no applied budget), the demand poll of an executor that says `reoffers` makes no demand for the next message (`holds_unbegun_reoffer()`, next to the first-start guard). Made then, it would name that process, and if the first message is taken back its retry becomes that process's only successor: the next message's demand could only end (`head_changed`). Once the turn has begun, or the first message has ended or been taken back, the next one is offered after the process that runs it. A demand that already exists is left to its own course, and a poll without `reoffers` is answered as before.
- The wait is bounded, once per message. A demand whose latest start said `reoffers` and whose process has stopped waits for the executor's evidence, whether or not the attempt had reported a process, and after a retry is opened it waits for the retry's start. The bound is counted from the demand's first process: `REOFFER_GRACE_MS` (3 minutes) after the later of that process's time-bound end (its last evidence plus `UNCERTAIN_GRACE_MS`) and the opening of retry 1. Later attempts do not move it. Once it has passed, the event ends (`head_changed`, block payload `"retry_lapsed"`, or `"head_changed"` once a budget was applied to the Agent): in the background cleanup worker, at the next poll, or at a retry request (which then opens nothing), and a start is refused (`shared_demand_not_current`, from `start_refusal()`). The worker ends each message in its own write and goes on past one it cannot end, as past an attempt it cannot stop, logging each by its id. An attempt whose start is committed has a process of its own and is not lapsed while it runs; if it ends without its turn after the bound, the event ends at once. So a message whose first process went silent and whose executor does not come back ends about 6 minutes after that process's last sign of life, 3 minutes after the time bound stopped it; one whose retry was asked for and not started ends 3 minutes after the first request, if that is later; and an executor that keeps coming back and going silent before the turn holds the Agent's queue at most that long plus the last attempt it started in time.
- A status shows a message given back only to a request that declares `reoffers: true`. For any other executor (a downgrade) an unbound message given back ends (`head_changed`, block payload `"reoffer_unsupported"`), whether or not a retry was opened or started for it.
- Chat status reports a message given back that then ended without a turn as any end of a waiting v2 message: state `blocked`, reason `head_changed`, and `endReason` from the demand's block payload (`retry_lapsed`, `reoffer_unsupported`, `retry_exhausted`, `retry_unsupported` or `head_changed`). Hagency Desktop reads that as "did not process" when the status names the Agent; a released Hagency Desktop up to rc.19 shows "Message could not start. Check the resource and Agent connection." instead. Its sender is offered to send it again (`canSendAgain`) while the Agent serves by the rule above. It reads one way whichever record ends it: once a budget was applied, the status, the budget queue's end and the bound's block all say `head_changed`.
- What happened is on record. The fence's record (migration `2026-11-26-000156`, re-created here) adds `stopSource` (`computer` when the process's stop or not-started receipt is recorded with the fence, `time_bound` when the server's time bound gave it up, `server` for any other decision), `released` (messages given back at this fence) and `releaseFailed` (releases that met the conditions and could not be made; a failed search counts as one). While the switch is on, the service also writes one log line after each committed release (demand, work and process ids) and after each failed one (with the SQLSTATE), from notes the database keeps in the transaction-local setting `hagency.shared_reoffer_notes`. On or off, it writes one when a block ends a message given back (`head_changed`; demand id and block payload). A Stop or an expiry ends such a message as any waiting one, without a line, and a budget block is no end. Lines carry ids and reasons only and are written only after their transaction commits.
- Four guards that made a binding permanent are relaxed for the released case only: delete on `management_shared_demand_bindings` and on `management_shared_event_pins` (the release row must exist and the work must be unstarted work of a fenced process), `bound` to `pending` on `management_shared_intake` (a release row and no binding), and the retry validator above. One guard is tightened: `fence_shared_unissued_work` also refuses to start released work. `validate_shared_demand()` is unchanged.
- Discovery advertises `shared-demand-retry-v2` next to `shared-demand-retry-v1` while the switch is on.
- Not covered: budget demands (v3) have no retry; a long-lived v1 process has no start to retry; an executor that does not say `reoffers` takes nothing back. Their events end as before. Their senders are offered "Send again" where the chat status says `canSendAgain`, also for a message that ended under the budget protocol.
- Rollback, in this order (`hagency-time-limits.md`, "Bringing the re-offer into service, and back"): switch it off; let what was taken back end; move the binary back to the reader release or later; run the down migration later, if at all. Executors do not stop sending `reoffers` by themselves: a saved start is sent again with its original bytes, and a retry's start carries `reoffers` from rows that never change. With the switch off the server still reads the field. It refuses a `stopped` receipt on the retry route (`invalid_shared_demand_retry`, recording nothing), so the executor reports it on the plain result route; a message already given back ends at its bound, at a read without `reoffers` or at that plain report, and an opened retry may still start. The reader release refuses nothing an executor sends. A release before it refuses `reoffers` (an unknown field), which is why every start that carried it must be finished before going further back. The down migration removes the release trigger, puts the four guards, the work-start guard and the fence record of `2026-11-26-000156` back, and keeps the release table with its guards and the functions they use (`shared_work_never_began()`, `shared_start_reoffers()`, `shared_agent_serves()` and `shared_agent_budget_applied()`); the chat status of this release calls `shared_agent_serves()` too. Run it only after the binary went back: this release applies the migration again at its next start.
- Schema: migration `2026-11-27-000159`: one additive table, the functions `shared_work_never_began()`, `shared_start_reoffers()`, `shared_agent_serves()`, `shared_agent_budget_applied()` and `note_shared_reoffer()`, one trigger on `management_shared_runtimes`, and replaced guard functions and fence record. Every statement can run again.
