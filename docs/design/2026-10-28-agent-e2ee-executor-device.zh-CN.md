# Agent 加密房间：执行端持有 agent 设备

日期：2026-10-28。状态：已决定，阶段 0 已通过。本文取代 `docs/CRYPTO_CAPABILITY_GAPS.zh-CN.md` 中“受限 crypto proxy、Matrix token 永不交给执行端”的方案，仅针对 agent 加密房间这一功能。

## 决定与信任模型

- 执行端（个人 agent 是主人设备，资源池 agent 是资源提供者设备）持有该 agent puppet 一个专用 Matrix 设备的 access token，用标准 matrix-sdk E2EE 客户端同步、接收房间密钥、解密、在本地判断是否被呼叫、加密回复。
- 用户已明确接受：资源提供者理论上可以绕过服务器检查，以 agent 身份发言。执行端本来就能看到明文（执行端日志保存请求正文，Codex 状态也在本机），服务器无法阻止执行端读取内容；原规则主要保护的是“agent 只回复已批准、已计费的任务”和撤销联动。
- 端到端加密的作用是把服务器、托管方和备份排除在外。执行端的保密靠组织管理（锁定的执行机、磁盘加密、无本地管理员）；个人资源提供者的情况靠明确告知与成员同意。
- 未加密的 agent 房间仍然支持，界面需标明“服务器管理员可读；@ agent 的消息在某设备上处理”。

## 架构

| 组件 | 职责 |
|---|---|
| 服务器 | 用 appservice 登录（`m.login.application_service`，指定 device_id）为每个 agent×执行端×加密代际签发设备 token，只交给当前持有执行租约的执行端；撤销时对同一 device_id 重新登录使旧 token 失效，或删除设备；继续负责绑定、审批、额度、记账、告警 |
| 执行端 | 每个 agent 设备运行一个带 SQLite 加密存储的 matrix-sdk 客户端：同步、密钥上传与补充、接收房间密钥、解密、本地判断 @ 与线程、调用模型、加密回复并发出、向服务器提交回执 |
| Palpo | 不改。固定版本已支持 appservice 设备登录、密钥、to-device、sync；无 fallback key，需保持足量一次性密钥 |
| 人类客户端 | 房间内按标准 Matrix 机制分享密钥；Desktop 为资源池工具审批接收 Olm to-device 详情并发送加密决定，资源主人无需加入房间 |

## 消息流程

1. 加密消息到达：服务器只看到发送者、房间、事件 ID、时间、线程关系（`m.relates_to` 不加密），以“候选”形式登记，不读正文、不预留额度。
2. 执行端经自己的同步收到同一事件并解密，判断是否在叫 agent：
   - 主人私聊：主人的每条消息都是请求；
   - 群聊：需 @ 或已登记线程的后续；
   - 资源池 agent：沿用现有规则（申请人在专用房间无需 @，其他成员需 @）。
3. 执行端向服务器确认“已被呼叫”（附事件 ID 与发送者），服务器照旧核验绑定、成员、额度与审批，生成任务并预留额度。服务器无法核验正文，信任执行端的这一确认。
4. 执行端调用模型，加密回复并以固定事务 ID 发出，再向服务器提交回执（事务 ID、事件 ID、用量）。数据库里“回复正文必须等于任务结果”的校验，对加密房间改为按事务 ID 与回执核对。
5. 非呼叫消息只在执行端解密后丢弃，不产生费用。

## 撤销、监控与权限

- 解绑、停止供给、执行端更换、设备吊销时：服务器对该 device_id 重新登录使 token 失效，必要时删除设备（Palpo 有 `delete_device` 管理接口），持久化并重试直到确认。换执行端时使用新的 device_id，不在机器之间复制私钥。
- 服务器监控 agent 设备发出、但没有对应任务回执的消息并告警，可选自动暂停该 agent。
- agent 在房间中只给发言权限，不给邀请、踢人、修改房间设置的权限。
- 执行端在任务完成后清除本地保存的请求正文，只保留记账所需数据；Codex 会话数据尽量不落盘或加密保存。

## 组织部署

- 支持组织管理的专用执行机（无界面的执行器，与 Desktop 共用引擎）。
- 资源池标明执行端类型（组织管理执行机 / 个人设备）；机密房间可要求只用组织管理执行机。
- 组织可要求执行设备经管理员批准后才能为资源池 agent 服务。

## 未决问题

- 加入前的历史：MSC4268（邀请时共享历史密钥）在 Desktop 与执行端所用 matrix-sdk 版本中的支持情况。
- agent 设备在成员客户端显示为未验证：交叉签名或验证体验。
- 服务器信任执行端“已被呼叫”的确认，用量归属可能被执行端误报。
- 执行端离线期间，服务器的候选登记如何过期与清理。

## 阶段 0 结果（2026-10-28，River，全部通过）

- **设备签发**：对已存在的 agent puppet（借用小白菜 `@_hagency_agt_01m5zes85dzsjag9qjc0fettd7`），appservice 登录指定 device_id `HAGENCYE2EESPIKE1` 成功，返回的 token 没有过期时间。River 上 Palpo 的 `/register` 对 appservice 也返回 “registration has been disabled”，appservice 登录要求用户已存在，因此只能为已有 puppet 签发设备。
- **执行端加密客户端**：用与 Desktop 相同的 matrix-sdk 0.19.1（`e2e-encryption`、`sqlite`、`automatic-room-key-forwarding`）从该 token 恢复会话，首次同步上传了设备密钥，创建加密房间并邀请 edward。
- **收**：edward 在 Rinx 中发送“加密测试”，执行端收到房间密钥并在本地解密。
- **发**：执行端加密回复（`encryption_info` 存在），约 1 秒后到达，edward 的 Rinx 正常解密显示。
- **服务器只存密文**：Palpo 中两条事件都是 `m.room.encrypted`（`m.megolm.v1.aes-sha2`），没有 `body` 字段，存储内容中找不到明文。
- **撤销**：服务器对同一 device_id 再次 appservice 登录后，执行端旧 token 立即返回 `401 M_UNKNOWN_TOKEN Token is not active`，新请求和正在运行的同步都失败，无需执行端配合。
- **清理**：客户端 `DELETE /devices/{id}` 需要密码交互认证，puppet 无法使用；改用服务器持有的新 token 退出房间并 `/logout`，设备及其密钥被删除，puppet 设备列表恢复为 `['appservice']`。

未覆盖：Hagency 服务器对加密事件的候选登记与执行端确认、多人加密房间、MSC4268 历史、成员客户端对 agent 设备“未验证”的提示、长期运行时的一次性密钥补充。验证程序源码只保存在本次会话的临时目录，未入库。

## 阶段 1 实现（2026-10-28）

主人私聊里主人的每条消息都是请求，所以阶段 1 不需要“执行端确认已被呼叫”这一步：服务器照常按路由信息登记派发，只是正文为空。

- **服务器**（hagency-server `3692acf`、`a6a4175`）：
  - 解析 `m.room.encrypted`，只取明文路由信息（发送者、事件 ID、线程关系），只有主人私聊接受加密事件。派发正文为空即表示加密。
  - `POST /hagency/api/v1/execution/e2ee-device`：持有当前租约的执行设备领取 agent 设备 token。设备 ID 由 agent×执行设备×代际派生（`HAGE2EE…`）。每次领取都会使该设备的旧 token 失效。另有 `/e2ee-device/revoke`。
  - `POST /hagency/api/v1/execution/replies/encrypted`：执行端发出加密回复后，服务器只记录事件 ID。回复正文为空、状态为 sent，事务 ID 与明文路径相同。
  - 明文的处理中表情、暂停提示和请求提示一律不发进加密房间。主人私聊的接入允许 Megolm。
- **执行端**（hagency-client `93e56126`，`owned_runtime/e2ee.rs`）：
  - 主人私聊工作线程启动时打开 agent 设备。首次同步上传密钥，让主人客户端此后为它分享房间密钥。
  - 状态存放在主人私有目录 `agent-devices/<sha256(agent)>/<device_id>`。SQLite 存储用随机口令加密，口令文件 `store-key` 权限为 0600。
  - 解密时最多等待 60 秒房间密钥。只接受文本消息，且事件发送者和 Megolm 会话的 Olm 认证发送者都必须是请求者。
  - 无法解密时在加密房间内提示主人重发，并以 rejected 结束，不调用模型。
  - 👀 由 agent 设备自己发出。
  - 回复格式与服务器一致：顶层私聊不加线程，线程内回复带 `m.thread`。超过 16 KiB 改为纯文本，超过 42 KiB 截断，确保加密后不超过 64 KiB 的事件上限。
  - 服务器拒绝记录回执（例如租约已换）时，不重发已送达的回复。
- **Desktop**（hagency-desktop）：本地 Agent 页面提供端到端加密开关，只能打开、不能关闭，打开前需确认。客户端对主人私聊的校验允许 Megolm。

已知限制：
- 旧版执行端会拒收空正文派发，必须先升级执行端再开启加密。
- 当时设备撤销尚未与解绑、换执行设备联动；2026-10-29 的本地实现见下文。
- agent 设备在成员客户端显示为未验证。
- 开启加密前发送的消息，agent 设备无法解密。

## 群聊、资源池与撤销实现（2026-10-29，本地代码）

阶段 2 的群聊接入和阶段 3 的加密文本执行链路已实现；此状态不代表已部署，
也不代表阶段 3 的全部审批体验已经验收。

- 加密群聊事件先登记有限期候选（每个绑定最多 10,000 条；轮转分页避免缺钥匙
  的旧事件阻塞后续事件）。执行端通过标准 Matrix SDK 接收 Olm/Megolm 密钥，
  验证解密消息的发送者，再按主人私聊、准确 @ 或已知线程判断是否呼叫 agent。
  确认只提交地址/线程元数据；未经确认不产生模型任务。确认结果不能在重试时改变。
- 资源池执行仍使用原预算、设备代际、调用托管和记账流程。加密任务的正文槽只
  保存原 Matrix event ID；本机保存并固定实际输入及最近的私人线程上下文，
  拒绝把 event ID 当作模型输入。回复由 agent 设备直接加密发送，固定事务 ID，
  本机持久保存送达证据。服务器只接受封闭的算法、房间、事件和送达状态回执，
  不接收回复正文，也不代发明文。撤销后已实际消耗的用量仍需如实报告。
- 原工具审批 API 会携带命令参数，因此加密资源池任务暂时在本机拒绝需要交互
  审批的工具调用；服务器也拒收这类明文审批登记。加密审批消息/UI 尚未实现，
  不能宣称与明文房间的所有工具审批功能等价。
- 设备签发、退休和撤销义务持久记录。解绑、停供、执行设备/代际失效后，后台
  重试登录并 logout 旧 Matrix 设备。先标记退休再尝试网络请求，避免 logout
  已成功但回执丢失时复用已删除发布密钥的旧 Olm 账户；恢复时签发新的 device ID。
  撤销依赖后台轮询和 Matrix 可用性，并不能收回执行端已经收到的明文或旧密钥。
- 个人 agent 密钥目录独立于模型提供者 HOME，按已认证的账户和执行设备隔离。
  私有 SQLite/文件保存解密输入、历史和原始回复以支持恢复，尚未实现任务结束后
  自动清除这些正文；资源提供者仍然是可以访问明文的受信执行端。
- 新建资源池房间要求服务器公布 `shared-agent-e2ee-v1`，创建时即设置 Megolm；
  现有房间和已保存的创建流程不自动转换。旧版执行端必须先升级。

验证覆盖：独立 PostgreSQL 上的候选、地址确认、预算执行、元数据回执、停供与
撤销重试；离线真实 provider probe 的私有输入和后续线程；本地 client 接入的
隔离 Desktop 编译。完整结果保存在客户端 `.run/e2ee-20261029/validation.json`。

- 命令参数与随机 32 字节 nonce 只通过 Matrix SDK 的 Olm 加密 to-device 传输。
