# Independent shared-process result tickets

Schema15 is a narrow correction on the qualified schema14 plus service-join source. It does not contain assignment-scoped durable intake, a new capability, or new runtime command/receipt fields.

The actual attempt2 trace showed initial Start, a background replay of the same saved intent, a background poll, then the original qualified upload returning `shared_result_ticket_changed`. Recovery could subsequently upload stopped. Both v1 and v2 previously stored only the latest result token/mode in the runtime row; an observation could invalidate a process still initializing under its original finite execute delivery.

`management_shared_result_tickets` stores independent hashed capabilities, bound to the exact runtime, executor device and generation, purpose, issue time and expiry. Delivery appends one ticket. Result handling validates the presented ticket and uses that ticket's purpose, never the most recent observer's purpose, when considering activity. All existing original command/receipt validation, ledger collision checks, generation and business authority, process fences, initial spawn deadline, policy flags and activity expiry remain mandatory. Historical observation still grants no fresh execution. If it uploads qualified evidence first while the exact original execute ticket and initial authority remain live, the receipt is retained but runtime stays issued with no activity. Subsequent recovery/poll cannot mistake that evidence for active lease expiry. Only presentation of the original live execute ticket can promote that same latest receipt; a newer stopped receipt, expired ticket/spawn deadline, or revoked authority prevents promotion. A stopped receipt remains immutable and cannot become qualified again.

Each ticket lasts at most30 seconds; execute expiry additionally remains bounded by the unchanged spawn command. A new observation does not extend an old ticket. At most64 active tickets exist per runtime. The existing PostgreSQL transaction advisory lock in `DomainStore::authorize` serializes issuance across independent service instances before count/insert. Issuance removes only already-expired tickets under database time and refuses at capacity without evicting a live ticket. SQL forbids mutation and live deletion. Ticket expiry collection never deletes process, call, usage, assignment or reservation history. Latest lease fields remain a compatibility/diagnostic projection, not result authority.

Migration preserves the last still-valid pre-migration ticket without changing its expiry, bound conservatively to the original assignment generation. Legacy rows did not record issuer generation, so a newer-generation cleanup holder must recover a fresh ticket; an old capability is never rebound to the current generation. Existing command and receipt bytes remain unchanged. The migration is atomic and exact-device replacement still blocks old execution; new-generation cleanup requires its own fresh observation/cleanup ticket.

Validation includes the exact real PostgreSQL/HTTP Start→replay→poll→original-qualified failure reproduced before the fix, v1 concurrent observation/discovery, purpose/token/role/generation denial, revocation, bounded live-ticket capacity, expired-only collection, immutable SQL history and atomic14→15 migration preserving an already-issued ticket. The full existing PG suite and strict lint are required before the release artifact is frozen. Root alone owns activation; the fix can use the existing Desktop22 wire protocol.
