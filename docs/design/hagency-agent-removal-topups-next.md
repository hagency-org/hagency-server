# Managed-agent removal and token increases

## Current behavior and bounded next checkpoint

The manager can cancel the original request and the current assigned project administrator can revoke approved admission. Both keep immutable request/agent identity and personal ownership constraints. The SQL dependency chain fences the admission intent, queues one native fence command, fences the assignment, expires shared activity, cancels unstarted work and preserves started work/reply uncertainty. Matrix cleanup retains the original puppet and room and observes membership after leave. These are separate facts: a recorded fence is not a later stop/settlement receipt, and an absent process is not complete usage.

Current methods are `management_agents.rs::cancel_managed_agent_request`, `management_agent_executor.rs::revoke_managed_agent_request`; cascades live in the executor, Matrix, shared-execution and shared-work SQL migrations. Existing routes erroneously require the issuance triple gate even for cancellation and recovery. The implemented cleanup checkpoint removes that requirement only for cancel, revoke and recovery of those two exact operations. Request and approval remain gated; authentication, device binding, actor role, CAS, immutable command digest and transaction remain unchanged. No executor policy is enabled by this change.

The cleanup checkpoint adds `agent-cleanup-v1` discovery for this restriction-only protocol, `GET agent-requests/{id}/removal`, and `POST agent-removals/list {projectId?,after?,limit?}` (limit 1–16). Reads authorize only the original manager or current assigned project administrator. The index filters authority and project before pagination. Detail exposes request identity/revision, exact `canCancel` and `canRevoke`, central fence state, native fence delivery and bounded receipt observations, latest separately labelled process observation, actual Matrix cleanup timestamp, and a nullable known-usage lower bound. No receipt bodies/digests, lease, prompt, provider identity, inferred free quota, aggregate runnable flag or refunded amount is exposed. No native receipt means unknown accounting. A late higher consumption observation forces reconciliation even if an older fence reported zero.

Acceptance: all issuance flags disabled while existing manager cancellation and assigned-admin revocation/recovery still work; manager cannot revoke as admin; resource owner/coordinator/server admin gain no implicit permission; admin replacement removes old actor's mutation/read authority; stale/changed command CAS fails; exact replay survives and observes latest state; rollback retains original histories; concurrent reserve/result/revoke preserves one cleanup command and no fresh execution. Read projection tests include native outcome unknown, later stopped process, Matrix cleanup pending versus observed, and positive late usage without refund inference.

## Original parity and the separate top-up protocol

Legacy `coordinator.rs::approve_coordinator_top_up` already uses a positive delta, expected current ceiling, canonical request identity, native headroom checks, one transaction and retained decision/publication receipt. `domain.rs::raise_allocation` similarly preserves spent usage and may lift only a quota hold. Their legacy engagement/coordinator authority must not be copied into the new business flow. The assigned project administrator approves an agent top-up; the native executor automatically checks already allocated project capacity. No extra resource-owner/coordinator human vote occurs.

The new managed child currently stores immutable original `allocated_tokens` and `budget_revision` (migration 077), and its reserve receipt binds those original values. Never overwrite either or alter original command bytes. The smallest complete top-up unit is:

1. Manager submits a positive same-period delta and bounded purpose, pinned to request/assignment/current budget revision, original reserve receipt and live project allocation. Persist a new request with pending/approved_waiting_executor/rejected/cancelled/expired/applied/refused/outcome_unknown states. Current assigned administrator alone decides with current authority revision. This does not enlarge the project or parent grant.
2. Central atomically records a closed `agent.budget.increase.v1` command containing original reserve command/digest, exact child and reserve receipt, assignment generation, request/decision digest, current administrator authority revision, expected budget revision and ceiling, positive delta, period, original enrollment/installation/resource binding, and finite expiry. Replays retain exact bytes. Only the exact current enrolled executor may apply; newer-generation same-installation recovery may upload historical evidence only.
3. Native adds append-only budget-adjustment rows and an `effective_budget` collector: original amount plus ordered applied deltas. A command CASes the current derived budget revision, checks all permanent fences/current profile, parent/project/resource/provider-account authority and same accounting period, and reserves only the delta from the existing project. Unknown sibling/call liability remains retained and cannot be called free. The same transaction stores an applied or definitive refused receipt with unique global ledger revision. Original child, call, usage and reserve evidence remain unchanged.
4. All managed child liability, call admission and fence/project/parent settlement collectors use the same effective ceiling. A top-up changes future call headroom only; it does not enlarge an already issued call or erase unknown/spent usage. It cannot clear a permanent fence, restart a stopped process, reassign an agent or mint new activity authority. If the first-turn process already stopped, successor lifecycle remains an explicit separate prerequisite.
5. Central reports increased capacity only after exact durable native receipt. A late applied receipt after cancel/revoke is retained as liability and cleanup continues; it never reopens admission. Unknown delivery remains pending evidence and cannot be replaced with a new command. UI shows original/current ceiling, positive requested delta, known consumed, retained/unknown values and accounting period separately. Missing observations remain null.

Proposed top-up routes are `POST agent-requests/{id}/topups`, `POST agent-topups/{id}/decide|cancel`, bounded read/list, exact command recovery and separate executor poll/recover/result. Schema/feature numbers are deliberately unreserved until native schema80 and central schema13 checkpoints freeze. Canonical closed fixtures must be shared before adapter implementation. Native raw JSON is not proof of assigned-admin authority or provider identity.

Required top-up tests: positive/exact-safe integer bounds; stale budget/authority/period; actor-role overlap without invented self-approval prohibition; original budget/receipt unchanged; concurrent delta versus call/reservation/release; overrun and missing usage; first lost response versus exact replay; process stop/revoke before and after native commit; old generation upload-only recovery; global revision collisions; rollback/restart; no automatic parent expansion; no legacy personal agent path changes. Full top-up is not claimed by the cleanup checkpoint.

## Cleanup source checkpoint

The implementation adds no schema migration and changes no reserve, fence, process, work or human-command bytes. Existing manager cancellation and current assigned-admin revocation/recovery remain available with all issuance flags false. An inactive manager does not prevent the authenticated current assigned administrator from reducing authority. The read API labels `proposedAgentId` explicitly; a pending request is not a provisioned identity. Historical native fence completion and later process/work observations remain separate. Unknown cleanup retains the original confirmed reservation floor; only a complete native fence can lower it, and later consumed usage raises the floor again.

Four isolated PostgreSQL/HTTP cleanup tests passed initially. The final focused run passed six tests in 11.04 seconds: disabled-issuance role/CAS/replay, current-admin replacement, inactive-manager restriction, cursor paging, real transactional rollback and concurrent reserve/cancel with exactly one cleanup command, plus both orderings of usage versus settlement. Evidence is in `.run/agent-cleanup-checkpoint/`. The combined full suite and strict Clippy are owned by the coordinator allocation read integration checkpoint; no new backend binary or live policy was activated by this work. Top-up remains design-only and requires its paired native accounting delta implementation.
